# C. Phase-resolved offline expert prediction

**Verdict: `BLOCKED`. No phase table is reported, because producing one requires a forward
pass through a 3 B-parameter model and this host cannot fork a process.**

---

## 1. Why it is blocked, precisely

The required quantity is `policy(observation_at_phase_k)` compared against
`expert_action_at_phase_k`, for k ∈ {reach, pregrasp, grasp, lift, transport, place,
release}. Every term needs `model.compute_loss` or `model.sample_actions` on a GPU. The
`Bash` tool fails at `fork(2)` before any interpreter starts (`README.md §0`), so the
measurement cannot be run, and no substitute number is offered.

This is the single largest hole in the audit: question Q4 ("which phase does the policy
leave the expert?") is the question that would tell the team whether they have a
*conditioning* failure or a *dynamics* failure, and it is unanswerable today.

## 3. Protocol (ready to run, not run)

1. **Segment phases from simulator truth, never from time fractions.**
   - *reach*: TCP displacement toward cube, gripper open (35 %)
   - *pregrasp*: TCP within 6 cm hover of cube, gripper still open
   - *grasp*: gripper command transitions 35 → 0
   - *lift*: cube z rises > 2 cm while gripper closed
   - *transport*: cube xy moves toward the target tray, cube z stable
   - *place*: TCP inside tray footprint, descending
   - *release*: gripper command 0 → open, cube separates from jaw
   Any window where two criteria conflict, or where contact state contradicts the gripper
   command, is labelled `UNKNOWN` and excluded. A phase table built by dividing episode
   length into seven equal parts is not acceptable and will not be produced here.

2. **Freeze the expert observation** at each phase entry, run 10-step prediction, and
   report: 10 joint MAE for the active arm, 2 gripper errors, per-horizon-step error curve,
   forward-kinematics TCP position/orientation error, and the motion magnitude of the
   *inactive* arm (the failure mode observed in closed loop is precisely inactive-arm
   motion, so this column is not optional).

3. **Separate the two error regimes explicitly.** Offline error at expert states is a
   *policy* error. Divergence after the state leaves the expert manifold is a *closed-loop*
   error and must be reported as a separate curve anchored at the first frame where the
   closed-loop state departs from the expert by more than the 95th percentile of expert
   frame-to-frame motion. Mixing them produces a number that describes neither.

## 4. Inherited, not re-measured

The brief cites "step-2000 expert-state offline joint MAE ≈ 1–3°, growing with horizon".
That figure is **carried over from the earlier diagnostic and was not reproduced here**.
It is quoted only so the eventual measurement has something to be compared against; it must
not be cited as this audit's result, and it should be regenerated by the harness because the
sampling of windows behind it is not documented in the artifacts that survive.

## 5. Acceptance criteria (fixed before the run)

| Outcome | Reading |
|---|---|
| error flat across reach/pregrasp, jumps at grasp or lift | the policy has not learned contact-rich transitions → conditioning or dynamics, not precision |
| error grows monotonically from reach onward | compounding open-loop error → horizon/execution issue, see E |
| inactive arm MAE ≈ active arm MAE at reach | the model is not selecting an arm at all → corroborates D |
| TCP error < 10 mm through transport, then diverges at place | placement geometry mismatch, e.g. tray pose convention |
